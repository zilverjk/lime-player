# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Lime Player is a Rust + Slint desktop audio player prototype focused on bit-exact playback of local or already-mounted NAS files (FLAC, WavPack, WAV, MP3) to an explicitly selected output device. `README.md` is the source of truth for playback scope and known limits; read it before changing audio behavior.

## Commands

Requires Rust 1.92+ (Slint 1.18 baseline) and CMake 3.5+ with a C/C++ toolchain (the `wavpack` crate builds bundled libwavpack). `.cargo/config.toml` sets `CMAKE_POLICY_VERSION_MINIMUM=3.5` so that build works under CMake 4.

```sh
cargo run                                   # debug build + launch
cargo test                                  # all tests (inline unit tests only)
cargo test --bin lime-player <test_name>    # single test (binary-only crate, no lib target)
LIME_SNAPSHOT_DIR=<dir> cargo test --bin lime-player render_snapshots -- --ignored
                                             # dev-only offscreen UI snapshots to PNG (src/ui_snapshot.rs); skipped
                                             # with a message when LIME_SNAPSHOT_DIR is unset, so plain `cargo test`
                                             # never needs a writable directory for this
LIME_REPAIR_FILE=<copy.flac> LIME_REPAIR_BACKUP_DIR=<dir> cargo test --bin lime-player repair_real_file -- --ignored --nocapture
                                             # dev-only: runs the sample-rate repair engine (src/audio/rate_repair.rs) on a
                                             # real file and checks rate/backup/no leftover temp file; rewrites the file in
                                             # place, so point it at a COPY on the volume under test (the manual regression
                                             # check for NAS/SMB shares); skipped with a message when LIME_REPAIR_FILE is unset
./scripts/package-macos-app.sh [dest.app]   # release build → ad-hoc-signed bundle, default dist/Lime Player.app
```

There is no rustfmt/clippy config; defaults apply. Tests are `#[cfg(test)]` modules inside `src/` files (`tests/` only holds decoder fixtures). No test touches real audio hardware or CoreAudio devices, and none registers a live OS media session (`MediaSession`, see "Media controls"): that would take over the developer's real media keys and Now Playing. `view_model::ui_contract` tests do string checks against `ui/*.slint` via `include_str!`, `main.rs` tests cover the pending-seek/timeline and Space-decision helpers, and `ui_snapshot::keyboard_tests` drive `MainWindow` offscreen with real Slint key/pointer events (Space, focus return, table selection) on every plain `cargo test`.

The Finder/`open` launch of the packaged app is the manual regression check for the async native file panel (see README).

## Architecture

`ui/app.slint` is compiled by `slint-build` in `build.rs`; it imports design tokens and every icon (`Theme`, `Icons`) from `ui/theme.slint` and shared widgets plus the Slint-side data contract types (`ui/widgets.slint`). `src/main.rs` wires Slint callbacks to `AudioPlayer`, the library scanner, and `AppState`, and polls both `PlaybackEvent`s and `LibraryEvent`s. All audio logic lives in `src/audio/`; the session library lives in `src/library/`.

### Threads and communication

- **UI thread** (`main.rs`): Slint event loop. `on_*` callbacks send `Command`s to the player; a 40 ms repeating `slint::Timer` drains the OS media session's `MediaCommand`s (see "Media controls") and then `PlaybackEvent`s with `try_recv()` and updates UI properties. The file picker is RFD's async panel scheduled on Slint's event loop — never a synchronous `runModal()` inside a callback.
- **Controller thread** `lime-audio-controller` (`PlaybackWorker::run` in `player.rs`): owns queue, lookahead, and active stream state; polls `Command`s via crossbeam with a short timeout.
- **Library scanner thread** `lime-library-scanner` (`LibraryScanner`, `src/library/scanner.rs`): probes newly opened paths (`audio::probe_file`) and reads their tags/lyrics/artwork (`audio::metadata`) off both the UI and controller threads. The controller never calls `probe_file` or `read_metadata` itself outside tests (via `fixture_track`) — every `PreparedTrack` that reaches `enqueue`/`play_next`/`ReplaceQueue` was already probed by the scanner. A later `scan()` request's phase 1 (probe) always runs before an earlier request's remaining phase 2 (tags/artwork), so a large first batch over a slow NAS share never blocks a later "Open Files…" from enqueuing and playing promptly; each request still gets its own `BatchDone` once its own phase 2 finishes.
- **Rate repair worker** `lime-rate-repair` (`RepairWorker`, `src/library/repair.rs`): owned by the scanner thread, repairs one non-standard-rate FLAC at a time off every other thread — see "Sample-rate repair" below. Absent unless the setting is on.
- **Decoder threads** `lime-audio-decoder` (`spawn_track_preparation`): one for the current track plus at most one speculative lookahead, plus up to `MAX_RETIRING_DECODERS` (4) retiring ones — a stop never joins its decoder inline (a NAS read may block), so it moves to `retiring_decoders` for `reap_retiring_decoders` to reclaim. Every immediate-stop path (`seek_to`, `replace_queue`, `previous_track`, `restart_current_from_queue`) refuses once that cap is hit rather than piling up unbounded blocked threads. They push `PcmSample`s into an `rtrb` SPSC ring buffer (`RING_SAMPLES`).
- **CPAL output callback** (`build_stream`): pops from the ring buffer and communicates back only through atomics (buffered count, eof/drained/output_failed flags, consumed-sample counter, diagnostics). Keep it real-time safe: no locks, no allocation, no blocking.

### Session library and view layer

- **`src/library/`** — the session library (`mod.rs`): every opened track, keyed by `TrackKey { path, start_frame, end_frame: Option<u64> }` (see "CUE sheets" below), grouped into albums and artists; the decoded values themselves are session-only, rebuilt by re-scanning at each startup. `scanner.rs` is the `lime-library-scanner` thread above, plus `LibraryScanner::scan_folder`, which spawns a dedicated `lime-library-folder-walk` thread per folder scan so a slow NAS walk never blocks other in-flight requests. `walker.rs` is the pure, cancellation-safe recursive directory walk "Open Folder…" and the startup folder rescan use, and also defines `has_cue_extension`/`CUE_EXTENSION`. `cue.rs` is CUE-sheet parsing, frame math, and file resolution/dedup — see "CUE sheets" below. `store.rs` persists *which* files/folders/cue sheets to re-scan (`library.json`, see "Persistent library" above) — never the scanned content. `repair.rs` is the sample-rate repair worker (see "Sample-rate repair"). `format.rs` is pure, I/O-free display-string formatting (track/album subtitles, clock strings, library summaries) shared by `app_state.rs` and `view_model.rs`, plus `aggregate_album_format` (album format-pill aggregation, see "Album format pill" below).
- **`src/app_state.rs`** — UI-thread state: the session `Library` and its decoded-artwork cache, `Navigation` (view stack, back button, artist/album filters, and the live search query — see "Search" below), and pure now-playing/pending-volume helpers.
- **`src/view_model.rs`** — pure projections from `Library`/`AppState`/`QueueTrackSnapshot` values to the generated Slint structs (no Slint window, no I/O), plus the `.slint`-source contract tests (`mod ui_contract`), e.g. no mock catalog strings remain, every icon reference resolves to a file on disk, and every typography token is used consistently.
- **`src/ui_snapshot.rs`** (test-only) — renders `MainWindow` offscreen with Slint's software renderer to PNG files from synthetic data local to the module; never constructs `AudioPlayer` or opens a device. See Commands above for the exact invocation. The same module also hosts `keyboard_tests`, which need the same offscreen platform (Slint keeps its platform per thread, so each test installs its own) but run on every `cargo test`.

### Album grouping

`Library::album_key`/`album_key(&TrackRecord)` never trust one track's own `ALBUMARTIST` tag in isolation — a real-world release is often tagged inconsistently (a stray file with no `ALBUMARTIST` at all, a duet/bonus track tagged with a combined artist, or a disc where every track individually credits a featured guest and no track carries `ALBUMARTIST` at all). Instead `Library::upsert`/`remove_album` resolve one "effective album artist" (`EffectiveAlbumArtist`, stored on each `TrackRecord`) per group of tracks sharing a (normalized album title, grouping-scope directory) — including CUE tracks of one sheet — via `resolve_effective_album_artist`'s three-step fallback:

1. The majority non-empty `ALBUMARTIST` among the group's tracks. A CUE-derived track's `ALBUMARTIST` is already the sheet's own `PERFORMER` once the sheet has one (`scanner::merge_cue_tags`), so a cue sheet's `PERFORMER` reaches this step automatically with no separate code path.
2. Otherwise, the dominant PRIMARY artist: each track's own `ARTIST` with a trailing featured-guest credit stripped (`strip_feat_suffix` — `"Dua Lipa feat. Miguel"` -> `"Dua Lipa"`; only ever `feat`/`ft`/`featuring` markers, bracketed or inline — never a blind `&`/`x`/`with` split, which would wrongly break a real band name like `"Earth, Wind & Fire"`, `"Simon & Garfunkel"` or `"Florence + The Machine"`), majority-voted; a stylistic featuring credit spelled with `&`/`x`/`with` on a minority of tracks (`"<winner> & Guest"`) still folds into an already-established majority (`dominant_primary_artist`). One artist covering at least `PRIMARY_ARTIST_MAJORITY_THRESHOLD` (60%) of the group's tracks wins.
3. Otherwise, the folder-scoped "Various Artists".

Every track in the group gets the same resolved value, recomputed from scratch (so it stays deterministic regardless of scan order) on every insert/remove. The album key itself then keys on that resolved artist plus the title, not the folder — so a release split across `CD1`/`CD2`, or ripped once to FLAC and again to WavPack in a sibling folder, still merges into one album/card as long as the resolved artist agrees, and a folder-scoped "Various Artists" bucket still separates two unrelated compilations that happen to share a title.

**Multi-disc subfolders.** The "grouping-scope directory" a track's group and folder-scoped keys (`va:`/`af:`/`dir:`) use is normally its own parent directory, but `grouping_scope_dir` walks one level up when that parent's own name looks like a disc/CD subfolder of a larger release (`is_disc_subfolder_name`: `CD1`, `CD 1`, `CD01`, `Disc 1`, `Disk 1`, `Disc One`, `"Disc 1 - Bonus Tracks"`, `"CD1 (Remastered)"`, case-insensitively — never a bare `"CD"`/`"Disc"` with no number, or a lookalike word like `"Disco"`/`"Discography"`) — so `CD1`/`CD2` resolve as ONE group and merge into one album (or one "Various Artists" bucket) instead of two. `DISCNUMBER` remains the ordering key only (`Library::album_tracks` sorts by `(disc_number, track_number, ...)`); it is not itself used to detect a disc subfolder, to avoid false positives from an unrelated pair of same-numbered albums.

**Artwork.** An album's thumbnail is chosen by precedence tier, highest first (`ArtworkSource`, whose derived `Ord` is the one priority order — do not reorder its variants): (A) `Folder`, a named folder cover — an image whose stem is `cover`, `art`, `album art` (also `album_art`, `album-art`, `albumart`), `album` or `front`, checked in that priority order, `.jpg/.jpeg/.png`, case-insensitive, whole stem only (`AlbumArtSmall.jpg`, `artwork.jpg`, `cover.gif` never match) — in the track's own folder, then, for a track inside a disc subfolder, in the RELEASE folder above it (a multi-disc rip's cover often isn't duplicated into every disc subfolder; own folder beats release folder); (B) `Embedded`, the track's own embedded picture; (C) `FolderFallback`, the legacy `folder.jpg/.jpeg/.png` (own folder, then release folder) — used only when neither A nor B produced anything, so an album with no embedded art and no named cover keeps its thumbnail. A candidate that cannot be read or decoded (unreadable, not a regular file — a symlink to a FIFO or device is refused, the read itself is capped at `MAX_ART_BYTES` — over `MAX_ART_BYTES`, corrupt, or a decoder panic, contained per candidate by `contain_panic` so it costs the picture and not the track's tags) falls through to the next ranked file, then the release folder, then B, then C. The requirement behind the order: a picture named like a cover beats whatever is in the tags.

Determinism is per album, not per track, because the scanner streams tracks in and the same album key can be reached from several folders (`CD1`/`CD2`, or a FLAC folder plus a WavPack sibling). Two pieces cooperate. The scanner thread keeps the best `ArtworkSource` already sent per approximate album key, per scan batch (`BatchArtwork::tiers`, owned by the batch's `BatchState`, so it is dropped with the batch however the batch finishes), and `attach_artwork` calls `resolve_artwork(.., best_so_far)`, which looks only for a strictly better picture: once Tier A was sent the batch never resolves that album again, an embedded-only album decodes its embedded picture once instead of per track, and a later folder's `cover.jpg` still gets through after an earlier track's embedded picture. The dedup is per batch, not scanner-lifetime, on purpose: a later request can land tracks on an album key that has no cached picture yet (after "Remove from Library" only part of an album may be re-opened, and its group can then resolve to a different effective artist, i.e. a different final key), and a lifetime map would keep suppressing the picture such a key needs; `AppState` keeps the best tier across batches, so resolving once per batch is enough. Each request also carries a snapshot of the exclusion set (`ScanRequest::excluded`, taken in `main.rs` at dispatch, after `include_path`/`include_folder` lifted what an explicit re-open overrides): `main.rs` drops an excluded track's `Scanned` record, so an excluded key never records a tier in `BatchArtwork::tiers` and never carries a picture — otherwise, say, a removed `01.flac` beside a newly added `11.flac` would spend the folder's `cover.jpg` on a record that is thrown away and leave `11.flac` with the placeholder. Phase 2 itself still reads the excluded track's tags and still reports it, and the snapshot cannot see a track excluded after its batch was dispatched (that batch's dropped record can still suppress a sibling's picture until the album is next opened). The key is only approximate (`album_key` of a transient, `Unresolved` record): a wrong guess usually costs one extra resolve, but two different albums colliding on the unscoped `aa:` key (same title and `ALBUMARTIST`, e.g. one folder with a mistagged stray track) inside one batch can let the first one's picture suppress the second's, which then keeps the placeholder. What the batch knows about folder images lives in `BatchArtwork::folder_reads` (`FolderPictureReads`) and is dropped with the batch, like `tiers`, so an explicit re-open or any later scan sees the folder as it is by then: a `cover.jpg` dropped in, renamed or repaired after the folder was first scanned is found by the next request and, at Tier A, replaces the embedded picture the earlier one produced (`AppState::cache_artwork`), and a failure — a `read_dir` that hit an SMB timeout while a share reconnected (kept as an empty listing for the rest of that batch, so the batch does not hammer the share), a candidate that could not be read — is never remembered beyond the batch it happened in. Within a batch, `FolderPictureReads::listings` does one `read_dir` per folder and stores the ranked Tier A/C candidate paths plus an `unusable` flag on each candidate whose read produced no picture (not a regular file, over the cap, corrupt, a decoder panic, an I/O error) — set BEFORE the read and cleared only on success, so even a read that unwinds is not repeated — so a corrupt cover on a NAS share is read once per batch, not once per track; it holds paths and flags only, never pixel buffers, and a cover that changes on disk while its batch is still running is not noticed until the next one. The lookup falls through to the next candidate like any other failure, so if a folder holds several named covers the lower-ranked one can be the picture that reaches `AppState` (a later scan that can read the higher-ranked one replaces it, being the same tier). `FolderPictureReads::last_picture` also holds the last folder picture the batch decoded (one thumbnail): every new approximate album key resolves from scratch, so tracks of one folder that each land on their own key (a different `ALBUMARTIST` per track, or many single-track albums sharing one `cover.jpg`) would otherwise each read and decode the same cover from the share again. The source rides on `TrackRecord.artwork_source` to the UI thread, where `AppState::cache_artwork(key, pixels, source, contributor)` files the picture under the album key next to the other contributors' pictures. The contributor is the resolution group (`library::resolution_group_key`: normalized album title + grouping-scope directory) of the track that carried it, and `AppState::art_cache` keeps at most one picture per contributor per key: a contributor's new picture replaces its own unless it ranks lower — so a `cover.jpg` replaced or repaired on disc (an equal tier, e.g. the `front.jpg` that stood in for a corrupt `cover.jpg`) is picked up by the next scan of that album, while a partial re-open that only sees a lower tier (one `CD2` track without the cover) can never downgrade it. The picture shown (`artwork_for_key`) is the highest tier among the key's contributors and, on a tie, the one whose contributor reached the key first (a picture moved onto the key counts from when it arrives; a contributor's replacement keeps its place). Contributors whose pictures have identical pixels share one `slint::Image` (`place_artwork` reuses the held picture's reference-counted buffer, checked by comparing bytes), so the same cover in a FLAC and a WavPack sibling folder costs one decoded thumbnail; different pictures from several contributors are all kept, one buffer of up to about 480 KB each, for the session. Pictures follow their contributor: when `Library::upsert` re-resolves a group onto another album key, `apply_scanned` moves that group's pictures with it (`move_artwork`) — whether or not the old key is left empty, and every picture when it is — so a compilation folder without `ALBUMARTIST`, whose first track ("Queen") resolves alone onto `aa:queen|greatest hits` beside Queen's own album of that name, hands its cover back off that key once ABBA's track turns the group into "Various Artists", and Queen's own picture is shown again instead of staying displaced; the outcome no longer depends on which track arrived first. That shared key is still real for as long as the group is one track: the compilation's cover shows on Queen's album until the second track arrives. Each shown picture carries a revision (`AppState::artwork_revision_of(&TrackKey)`: the revision of the picture shown for that library track's album, `None` when the track is not in the library or its album has no picture); the `Scanned` handler in `main.rs` reads it for the now-playing track before and after `apply_scanned` and re-projects the now-playing panel when it changed (or when the record is the playing track's own), so a sibling track's higher-tier picture (`cover.jpg` in `CD2/` replacing the embedded picture playing from `CD1/`) reaches a panel that is already showing the older one. Another album's picture never re-projects it, and neither does anything for a playing track that was removed from the library (its projection would only be the filename fallback and would blank the art, artist and lyrics the panel shows). "Remove from Library" forgets the removed album's pictures (`AppState::remove_album`), so re-opening it starts from what is on disc by then. Only what a later scan can add or replace is picked up in a running session: a named cover that is new (tier upgrade), replaced or repaired is; one that was DELETED is not (a lower tier never replaces, by design, so a partial re-open cannot downgrade an album) — the album keeps showing it until "Remove from Library" and a re-open, or the next launch, whose cache is rebuilt from scratch. This makes the chosen TIER independent of scan order; within one tier and one contributor the newest picture wins (a different `cover.jpg` in each of `CD1/` and `CD2/`, which share a group, or a different embedded picture per track that the scanner sends for different approximate keys), between contributors the one that reached the key first wins (a different `cover.jpg` in each of a FLAC and a WavPack sibling folder), and picking the picture from the first track in (disc, track) order is not implemented. CUE tracks (`build_cue_track_records`) go through the same `attach_artwork` (same tiers, same per-batch dedup, so a multi-`FILE` sheet reads its cover once) and attach the picture and its source to the first non-excluded track built from each physical file.

**The artwork-cache-key bug.** A real two-disc release (`CD1`/`CD2`, no `ALBUMARTIST` anywhere, `CD1` tagging a couple of tracks with a featured-guest credit) could show its `CD1` group with a placeholder (no artwork) even though its FLACs have embedded pictures: the scanner resolves a track's art the first time its (then-current) album key needs one — and skips a later track that could not improve on it — and the UI thread caches it in `AppState`'s `art_cache` under that key; but `Library::upsert` re-resolving a GROUP (e.g. the majority flipping between a lone track's own `ARTIST` and `VariousArtists` as more, differently-tagged tracks joined) can silently move an ALREADY-CACHED sibling track onto a different key as a side effect, and nothing re-cached the art under the new key — it was orphaned under the abandoned one. `Library::upsert` now returns every `(old_key, new_key)` transition a call caused, including a sibling's, not only the just-upserted record's own; `AppState::apply_scanned` migrates the artwork cache for each one (the moved group's pictures, or all of them once the old key is fully vacated — see "Artwork" above) and `recent_album_keys` once the old key is fully vacated, and reports every vacated transition so `main.rs` rewires `Navigation` (back stack, current entry) too.

### CUE sheets

Opening a folder or files whose directory contains one or more `.cue` sheets uses the sheet(s) to define that folder's tracks instead of scanning each audio file as a whole track; a `.cue` file can also be opened directly via "Open Files…". `src/library/cue.rs` parses a sheet's global `PERFORMER`/`TITLE`/`REM GENRE`/`REM DATE` and each `TRACK`'s `TITLE`/`PERFORMER`/`INDEX 00`/`INDEX 01` (`parse_cue`), and converts an `INDEX 01` timestamp to a sample frame of the resolved audio file via `cue_time_to_sample_frame` (`(mm*60+ss)*rate + ff*rate/75`, 75 frames/sec per the CUE/CD-audio timing base). Multiple cue sheets in one directory that resolve to the same audio file(s) are deduped by `dedupe_cue_sheets`, preferring a sheet whose `FILE` resolved directly over one resolved via a stem/extension or single-file-in-folder fallback (`resolve_cue_files`).

`scanner.rs`'s `expand_cue_sheets_for_paths`/`expand_one_cue_sheet` run this as phase 1 only (probe + `TrackKey` math for every track) — tag/artwork reads for cue-derived tracks stay in phase 2 like any other track, preserving the phase-1/phase-2 ordering guarantee above. A per-file probe failure fails only that file; a sheet-level failure (parse error, an unresolved `FILE`, or `INDEX 01` timestamps that do not strictly increase within a `FILE`) fails the whole sheet as one `LibraryEvent::Failed { phase: Cue }` (shown as a status-line message), and every file it would have claimed falls back to ordinary whole-file scanning.

Track identity is `TrackKey { path, start_frame, end_frame: Option<u64> }` (`library/mod.rs`), which replaced a bare-path identity everywhere in the library/scanner/player/UI-projection layers. `TrackKey::whole_file` gives the old `start_frame: 0, end_frame: None` identity; a cue sub-range track has both set in sample frames of the physical file (`end_frame` exclusive, `None` only for a `FILE`'s last track). `track_key_string` renders the Slint-side `TrackRowData.key`/`now-playing-key` string, appending `#{start_frame}` only for a sub-range track so two cue tracks of the same file never collide.

A CUE sub-range track decodes with an explicit `start_frame`/`end_frame` (`decoder::decode_file`/`decode_symphonia`/`decode_wavpack`), truncating exactly at `end_frame` so it never reads into the next track's samples; duration is `end_frame - start_frame`. The controller's Timeline/seek math is track-relative: `track_relative_millis` subtracts the active track's own `key.start_frame` (0 for a whole-file track) before emitting `PlaybackEvent::Timeline`, and `seek_to` adds it back (`key.start_frame + relative_frame`) to get the absolute physical-file decode frame — so a cue track's on-screen position/duration and drag-seek always read 0:00 at its own `INDEX 01`. Two consecutive cue tracks from the same physical file still go through the normal next-track path (same device/rate/Hog lease, no renegotiation, see "Track transitions" above) and still get their own fresh CPAL stream like any other track change — there is no gapless handoff between cue tracks; this is an accepted, unaddressed limit (see README "Known limits").

### Format pills

Every album card (Home, Albums, Search, Artist-albums grids) and the album-detail header shows a small pill next to the title/meta area with the album's format aggregated across all its tracks: `Mp3`/`Flac`/`WavPack`/`Wav` when every track shares that format, `Mix` when more than one is present (`AlbumFormat`, `library/format.rs`). `aggregate_album_format` computes it once per album, in the same pass `summarize_album` already makes over the album's tracks, and the result is cached on `AlbumSummary.format_label`/`format_variant` rather than recomputed per render. `ui/widgets.slint`'s `FormatPill` component renders it, colored by `variant` (`"mp3"`/`"flac"`/`"wavpack"`/`"mix"`/`"wav"`) via `ui/theme.slint`'s `flac-*`/`wavpack-*`/`mix-*`/`wav-*` tokens; `"mp3"` reuses the existing `accent-soft`/`accent-strong` tokens (the app's lime accent). The neutral grey WAV pill was an implementation decision, not explicitly specified by the original request.

Each `TrackRow` shows the same `FormatPill`, colored the same way, next to the track's own title — this replaced an earlier lime-green "Hi-Res" `Badge` that flagged bit-depth/sample-rate thresholds (`is_hi_res`, now deleted) instead of the track's format family. `track_format` (`library/format.rs`) reuses `aggregate_album_format` on a single-element iterator to map one track's `AudioInfo.format` string to its `AlbumFormat` (never `Mix` in practice — that only happens for two or more distinct formats). `TrackRowData.format_label`/`format_variant` carry it to Slint (`view_model.rs`'s `track_row_from_record`/`build_track_row`). Where a row also shows the separate Format column (Songs, Recently Added, Search, Queue — `show-format: true`; album detail leaves it off), that column's `FormatPill` keeps the bit-depth/rate `badge` text (`format_badge`, e.g. `"FLAC 24/96"`) but colors it with the same `format_variant` instead of the neutral `Badge` it used before.

### Search

Typing in the top-bar search field shows a dedicated Search view (`SearchResultsView` in `ui/app.slint`) instead of whatever `view` the sidebar last selected, with three sections — Songs (a plain, non-virtualized `TrackTable`, since it shares one `ScrollView` with the other two sections and so cannot own a `ListView`; capped at 200 rows, `SEARCH_SONGS_LIMIT` in `view_model.rs`), Albums (the usual `AlbumGrid`, capped at 48, `SEARCH_ALBUMS_LIMIT`) and Artists (`ArtistListRow`, shared with `ArtistsView`, uncapped) — each hidden when empty and headed by a count or a "Showing first N of M" note (`format_search_section_header`, `library/format.rs`) so a cap never truncates silently. All matching is case- and accent-insensitive (`normalize_for_search`/`track_matches_query` in `library/mod.rs`) across title, artist, album, album artist and genre.

`Navigation` (`app_state.rs`) owns the query, not `main.rs`: `search_active()` (query non-empty after trimming) is what the Slint side actually gates on (`MainWindow.search-active`, pushed by `sync_navigation`/`on_search_edited`), and `current` (the view/nav_view/artist_filter/album_key underneath) is never touched by the query — so clearing it (Esc, the pill's own "x", editing back to empty) always lands back on exactly whatever was already current, with no separate "previous view" to restore. `nav_selected`/`album_opened`/`artist_opened` all clear the query as part of navigating, so opening an album or artist from the Search view's own results actually navigates there instead of leaving the Search view stuck on top of it.

### Playback pipeline and output routes

Library scanner: opened path → `decoder::probe_file` → `PreparedTrack` → `AudioPlayer::enqueue`/`play_next`/`replace_queue`. Controller: `PreparedTrack` → `start_track_prepared` (resolve device, Hog lease, set nominal rate, wait for prebuffer, `build_stream`, re-verify physical format, `play()`).

The route is decided only by `uses_strict_integer_route(&AudioInfo)` (`player.rs`), called from `spawn_track_preparation` and `start_track_prepared`; never inline the predicate again — besides its own definition and tests, `rg -n uses_strict_integer_route src` must show only those two call sites:
- **Strict integer route** (macOS, integer PCM): samples are left-aligned into I32, the CPAL stream is requested as I32 at the exact source rate, and playback is refused unless CoreAudio's physical stream reads back as exact-rate packed signed 32-bit stereo LPCM. Mono is refused, not upmixed.
- **Float fallback** (float WavPack, MP3, non-macOS): F32 stream, labeled "not bit-perfect" in the UI.

### macOS CoreAudio (`src/audio/coreaudio.rs`)

A `cfg(target_os = "macos")` `platform` module does raw `AudioObject*PropertyData` FFI; a non-macOS stub returns errors. It provides `HogLease` (RAII; `Drop` releases only if this process still owns the device), `set_and_verify_sample_rate` (set + readback), and physical ASBD verification/selection. CPAL only reports the virtual callback format and may renegotiate the physical format while building a stream, which is why the physical format is re-checked after `build_stream` and just before `play()`.

### Track transitions

`reconcile_lookahead` pre-decodes the next queued track; `preparation_for_start` reuses it when the path still matches. `advance_if_drained` tears down the stream only after the callback reports `drained` and `OUTPUT_DRAIN_GUARD` (90 ms) has elapsed, then the next track builds a fresh stream. Every track gets its own CPAL stream because each callback owns its track's ring-buffer consumer and atomics — same-rate gapless handoff would require redesigning that ownership. Shutdown cancels lookahead first and uses `join_decoder_until` with a grace period because NAS reads can block in non-interruptible syscalls.

`start_track_prepared` (macOS) also primes the DAC before building the real stream whenever `needs_dac_prime` detects a rate, physical-format, or route change (strict integer ↔ float) versus the last stream this same device actually had active — including a route change the HAL's own before/after `build_stream` snapshot can miss, since the float route never pins an exact physical format. Priming plays a throwaway zero-filling stream on the same device/config briefly, then pauses and drops it, to reproduce the "press play again" workaround that reliably clears a DAC left on the previous track's clock/route. `LIME_DAC_PRIME_SETTLE_MS` controls the settle time on each side of that stream (default 150 ms; `0` disables priming). The real stream that follows a primed start writes a silent pre-roll before the first track sample so the track's audio isn't lost while the DAC un-mutes/relocks; `LIME_DAC_PREROLL_MS` controls its duration (default 1000 ms, clamped 0..=3000, `0` disables it).

### Seek

`AudioPlayer::seek(path, position_ms)` sends `Command::Seek`; the controller's `seek_to` computes the target decoder start frame (`seek_target_frame`, clamped to the track's known duration — a file that never reported a duration refuses any nonzero seek), stops the active stream (`stop_active_now`), and rebuilds it through the same `spawn_track_preparation` / `start_track_prepared` path a fresh track uses, except pinned (`StartOptions::pinned_output`) to the *same* output device, Hog lease, and nominal rate the track was already using — a seek can never trigger a device change or a rate renegotiation; a successful seek reuses the existing Hog lease unchanged, but a failed seek (`fail_seek`) releases it and leaves the track blocked at the queue head, since the restart itself never happened. A stale path (the track already advanced), a skip already pending, a failed decoder/output, or an unsupported duration are all refused via `reject_seek`, which emits `SeekRejected` plus the current `Timeline` so the UI clears any pending seek state immediately instead of showing a scrubber stuck mid-drag.

### Media controls (media keys, Now Playing, Space)

Keyboard media keys (F7 previous / F8 play-pause / F9 next), the Control Center / menu-bar Now Playing widget, and the window's Space key all end in the same `AudioPlayer` calls the on-screen buttons use. macOS routes the media keys to whichever app registered as the Now Playing client, so before this the keys went to Music.app; the fix is registering with MediaPlayer, not intercepting key events (winit does not surface them).

**`src/media_controls.rs`** has two layers. The parent module is pure and platform-independent, and it is where the unit tests live: `MediaCommand`/`SeekDirection`, `NowPlayingState`, `plan_media_command` (command -> `TransportAction`, given the UI's play state), the hold-to-seek stepping (`HoldSeek`, `hold_seek_target`), and what to publish (`plan_transport_publish`, `timeline_needs_publish`, `PublishedTransport`). `platform` is the FFI bridge: on macOS it uses MediaPlayer's `MPRemoteCommandCenter` (commands in) and `MPNowPlayingInfoCenter` (metadata out) through `objc2-media-player`; elsewhere `MediaSession` is an inert stub with the same API, so nothing else branches on the platform. The macOS crates are under `[target.'cfg(target_os = "macos")'.dependencies]` with `default-features = false` and stay on the objc2 0.6 line (`objc2` 0.6, `block2` 0.6, `objc2-foundation`/`-app-kit`/`-core-foundation` 0.3): winit pulls the older 0.5 line, so never pass winit's `NSWindow`/`Retained` types into these.

- **Threads.** MediaPlayer does not document which thread runs the command handlers, so they must work from any of them: they only `send` a `MediaCommand` into a crossbeam channel and return `Success`; everything else happens on the UI thread, where the queue/timeline/pending-seek state lives. `main.rs` drains that channel first in the 40 ms event timer, before the `PlaybackEvent` loop, and writes every command as a `DIAG media command ...` line. `MediaSession::new` is called from `main()` only (it needs the AppKit main thread, and a second one in the same process is inert, guarded by a static); it must never be reachable from `MainWindow::new()`, because `src/ui_snapshot.rs` builds windows on a software platform. The session, `HoldSeek` and `PublishedTransport` live inside the timer closure, the only thing that uses them.
- **A Lime that never played holds no keys; one that has keeps them while its play button works.** Every transport command starts disabled and is enabled by the first `publish`. `clear()` empties the widget, sets `playbackState` to Stopped and disables them again, so the keys go back to whichever app had them — but only when nothing is loaded AND the on-screen play button would do nothing (`TransportSnapshot::can_resume`, i.e. `play_button_enabled`: nothing has played this session and the queue is empty). With no active track but a working button — a track the controller kept blocked at the queue head after a failed seek or start ("Press Play to retry"), a track that can be replayed after the queue ended — `plan_transport_publish` keeps the session as a PAUSED one (last panel metadata, elapsed 0, no length, so nothing to scrub): macOS sends F8 to Music.app as soon as playback state is Stopped, so clearing there would make the keyboard and the play button retry in different apps. The session is published from the panel's metadata, so it exists only once a track has started this session: a first-ever start that fails (no output selected yet) leaves a queue but no metadata, `sync_media_session` clears, and F8 still goes to the system. The consequence is that after the first track has started, Lime keeps the keys (paused) until quit. `stop`, skip-by-interval, rate, rating and the rest stay disabled for good: the research behind this design expects a held F7/F9 to arrive as `seekBackward`/`seekForward` Begin/End only while skip-by-interval is off (with it on, other players see `skipBackward`/`skipForward` instead). That routing is not confirmed on real hardware (see the unverified list below); the fallback would be enabling the skip commands with a 5 s interval and treating each as one step. The scrubber command (`changePlaybackPosition`) is enabled only while the duration is known, since the controller refuses a nonzero seek without one.
- **Command mapping** (`plan_media_command`, run in `main.rs`). `TogglePlayPause` -> `toggle_playback` (the play button's path). `Play`/`Pause` toggle only when that would change the UI's `is-playing` (the controller only has a toggle; the flag is flipped locally after each toggle inside one drain so two commands in one tick do not read stale state). `NextTrack` -> `AudioPlayer::next`. `PreviousTrack` -> `AudioPlayer::previous`: the Apple Music rule (restart the track after 3 s, else go back) is already the controller's `previous_track`, so it is deliberately not repeated. `SetPosition` (a Control Center scrub) -> the seek path.
- **One seek path.** `SeekRequester::request` (`main.rs`) is the only place the UI asks for a seek: the on-screen scrubber (`request_fraction`), a Control Center scrub and every hold-to-seek step go through it, sharing the `can-seek` guard, the optimistic UI, the `PendingSeek` bookkeeping and the clamp to the duration (`seek_ui_target`).
- **Hold-to-seek** (`HoldSeek`, driven by `tick` from the same 40 ms timer, not a second `slint::Timer`). `SeekBegin(dir)` arms it (a repeated Begin for the same direction does not restart the delay; the other direction replaces it); the first step comes after 250 ms (so a quick Begin/End pair, e.g. from a Control Center click, is a no-op), then at most one every 400 ms and only while `pending_seek` is `None`. A step moves 5 s from the pending target, else from the last applied timeline position, clamped to `[0, duration - 500 ms]` (the controller's own clamp). The hold ends by itself when the clamped target is the one the previous step already issued (`ArmedHold.last_target_ms`: pinned at the start or the end — it never skips to another track), when the position already is the clamp (the paused case), or when the duration is unknown; comparing with the position alone is not enough, because a playing track keeps advancing after a step to 0 lands (and the pending-seek gate accepts any timeline within 1.5 s of the target, including the old stream's own), so the hold would rewind to 0 again, rebuilding the stream, every 400 ms until the key is released. It is disarmed by the matching `SeekEnd` (a late End for a direction a newer Begin replaced is ignored), `Started`, `Stopped`, `Inactive`, `SeekRejected`, and a 60 s fail-safe (an End can be lost). It works while paused, since a seek preserves the paused state. Every step is a full stop, decoder spawn and output rebuild (see "Seek"), so playback is silent between steps.
- **Now Playing publishing.** `media_dirty` (an `Rc<Cell<bool>>`) is set by `Started`, `Playing(bool)`, `Stopped`, `Inactive`, `SeekRejected`, every `SeekRequester::request`, a `Scanned` record that re-projected the playing track (real tags or a better cover arriving from the scanner), and an accepted `Timeline` that drifted more than `TIMELINE_DRIFT_TOLERANCE_MS` (750 ms) from where the widget extrapolates to, or that reports a newly known duration. Ordinary ~50 ms `Timeline` ticks are deliberately not forwarded: the system extrapolates from elapsed time and playback rate. `sync_media_session` then publishes at most once at the end of the tick from the final UI state (several events of one tick describe one change); it is the controller, not this batching, that keeps the widget from showing Paused between two tracks (see "Track changes keep the transport state"). What it publishes mirrors the now-playing panel: title/artist/album/cover are the panel's own last projection, `PanelNowPlaying`, which `apply_now_playing_projection` returns and the timer closure keeps (set on `Started` and on the `Scanned` re-projection, never cleared) — not a fresh `project_now_playing` at publish time, because the panel deliberately keeps the tags and cover of a playing track that "Remove from Library" took out of the library (and after `Stopped`/`Inactive`), where a fresh projection would be the file name, "Unknown Artist" and no cover and the widget would stop matching the app; playing = the UI's `is-playing` (rate 1.0 / 0.0), elapsed = the pending seek's target if one is in flight (a Control Center scrub must not snap back), else the last applied position, clamped to the duration; a zero or missing duration is published as no length. With no active track (`Stopped`/`Inactive`) but a working play button it publishes the panel's metadata paused at 0:00 with no length. Each publish builds a fresh `nowPlayingInfo` dictionary (always including the artwork key when there is a cover) and sets `playbackState` (Playing/Paused) every time — on macOS MediaPlayer requires that or the keys keep going to another app. The cover goes `slint::Image::to_rgb8()` -> `NSBitmapImageRep` -> `NSImage` -> `MPMediaItemArtwork` (no PNG round trip), cached per `AppState::artwork_revision_of` (taken when the panel was projected) so it is converted once per picture.
- **Next while paused** (`src/audio/player.rs`). A graceful skip only completes once the output drains, which never happens on a paused stream, so Next used to sit "pending" and a media key would look dead. `next_action()` now returns `NextAction::AdvancePaused` for a paused track with a successor (even if a graceful skip was pending before the pause): `skip_paused_to_next()` checks the retiring-decoder cap, stops the track immediately (`stop_active_now()`, the same immediate stop `previous_track` uses), pushes it to history (not `last_completed`: it did not finish naturally) and calls `start_next_paused()`, i.e. `start_queue_head(.., start_playing: false)`, so the next track starts paused (`StartOptions.start_playing = false`, as a seek restart does) through the ordinary start path — device, Hog lease and rate handling are a normal start's, and it reports `Playing(false)` itself. Next while playing is unchanged (graceful skip). Previous keeps the transport state the same way: going back (under 3 s with history) from a paused track loads the previous one paused (`was_playing` taken before the stop, `start_next_after_stop(None, was_playing)`), so F9 then F7 on a paused player never starts audio; with no active track, or while playing, it plays as before. That holds when the start has to wait for a lookahead decoder to stop, which is the common case (a paused track almost always has a lookahead for the queue's next track, and going back or forward makes a different track the head): `preparation_for_start` cancels the mismatched lookahead, finds its decoder still winding down and sets `waiting_for_decoder_cancel`, and `start_queue_head` records the requested state in `pending_start_playing`; `resume_start_after_decoder_cancel` (every loop iteration) consumes it, so the deferred start is made with the `start_playing` that was asked for, not with a hard-coded `true`. While a start waits (`active == None && waiting_for_decoder_cancel`) `pending_start_playing` IS the transport state, and only Play/Pause changes it: `toggle_playback` flips it and emits `Playing(new state)` instead of starting the head (Play pressed during a paused Next/Previous wait makes it a playing start; Pause pressed during a playing wait, after a replaced queue or a Previous while playing, makes it a paused one), while every request that is not a play/pause request preserves it. `start_next()` (Enqueue, PlayNext, SelectOutput, SetHogMode, Next with nothing active) passes `transport_playing_while_idle()` — `pending_start_playing` while waiting, `true` otherwise — instead of a hard-coded `true`, and `previous_track` uses the same helper when nothing is active, so a second F7 on a paused player, or F7 then F9, never turns the paused start into a playing one (the explicit Play in `toggle_playback` calls `start_queue_head(None, true)` directly). `next_track` with nothing active during a wait pushes the head it skips to history (a Previous had just taken it out of history and it never loaded); a blocked head skipped with no wait is still dropped without a history entry. `replace_queue` is an explicit play request, so it overwrites the pending state with `true`; when the UI was showing Paused (a paused track, or a paused wait) and the start ends up waiting, it also announces `Playing(true)` so a Play pressed in the gap acts on what is displayed. Known residual: a wait entered with nothing active and no wait in progress (a blocked head whose cancelled lookahead decoder is still stuck, then Enqueue/PlayNext/Previous) starts playing while the UI shows the earlier `Playing(false)`; there Play toggles the pending start off.
- **Track changes keep the transport state** (`src/audio/player.rs`). `stop_active_now()` never emits `Playing(false)`: every caller starts something right after it, and that start blocks (rate-change guard, DAC prime, up to 30 s of prebuffer wait on a NAS), so an announcement sent first would show the UI — and the OS widget, which mirrors it — as Paused for the whole gap, and a `Play` media command arriving in it would toggle the freshly started track back to paused. Instead `start_next_after_stop(observed_at, start_playing)` starts the queue head and sends `Playing(false)` only if `self.active` is still `None` afterwards (empty queue -> `Stopped`, failed start -> `Inactive`). A start that is only waiting for a lookahead decoder to stop (`waiting_for_decoder_cancel`) will happen, so nothing is announced then either: for `replace_queue` (double-clicking another row while playing) the old next-track lookahead almost never matches the new head, so this wait is the normal path, and a `Playing(false)` sent for it would flip the in-app play button and the OS widget to Paused, with the old track, through the whole start. `resume_start_after_decoder_cancel` makes the start via `start_next_after_stop` (so the same rule applies to its outcome) and, if it turns out there is nothing to start (queue emptied or head blocked meanwhile), sends the `Playing(false)` that was held back. The UI therefore keeps its previous transport state while the decoder stops (the "Waiting for the previous next-track decoder to stop…" status shows once); with a decoder stuck in a NAS read that can be a while. Play/Pause pressed in that gap acts on that displayed state, not on a forced playing start: `toggle_playback` flips `pending_start_playing` and announces it (see "Next while paused"). Used by the natural drain (`advance_if_drained`), `replace_queue`, Previous going back, `restart_current_from_queue`, and the completed-graceful-skip branch of `finish_active_failure`; a retained failure still reports `Inactive` then `Playing(false)` at once.
- **Space, focus and selection** (`ui/app.slint`, `ui/widgets.slint`, `main.rs`). `MainWindow` wraps its whole layout in `key-root := FocusScope` and sets `forward-focus: key-root` (nothing has focus at startup, and key events only travel the focus item's ancestor chain). Never `clear-focus()` on the field: that leaves no focus item and Space would reach nobody. **The row selection is a track key, not a position.** `MainWindow.selected-track-key` (`in-out string`, `""` = none) holds the `TrackRowData.key` of the row last clicked; `TrackTable`/`VirtualizedTrackTable` take it as `selected-key`, highlight `row.key == selected-key`, and report a click or double click as `selected(row.key)`; each view forwards the key down and the click up (`selected(string)`), and `MainWindow.row-selected(key)` releases the search focus and stores it (there is no `track-selected` callback and no "no selection" report from a table's `init` any more: a table appearing mid-typing reports nothing, so it cannot take the keyboard from the search field). A key is used because a table that stays on screen has its rows replaced all the time — Slint keeps an `if` instance alive while its condition stays true, and every library re-projection (`project_and_set_library`: a scan batch, `Started`) sets brand-new models — so an index would name whatever sits at that position now (an earlier version reset the index on `changed rows`, which fixed that but dropped a clicked row's highlight, and Space's target, within one re-projection, e.g. throughout a startup or Open Folder scan). With a key the highlight follows the track to wherever it sits after the re-projection and simply disappears when the track left the list. `main.rs` reads the key only when Space is pressed: `visible_selection` resolves it against the rows of the table on screen (`visible_track_list`: the Search table while a search is active, else the current view's; `row_of_key`) and drops it when that table does not hold the key. ### Diagnostic vs Status events

`PlaybackEvent` carries both a developer-only `Diagnostic(String)` and a user-facing `Status(String)`. `main.rs` prints every `Diagnostic` to stderr with a `DIAG` prefix and never surfaces it in the UI; `Status` updates the UI's status line. The controller routes plumbing signal-flag changes (decoder/callback nonzero-sample flags) as `Diagnostic`, unconditionally whenever they change (`emit_audio_diagnostics_if_changed`); a buffer underrun is a real, user-visible degradation, so it is instead a rate-limited `Status` (`emit_underrun_status_if_due`) so it stays visible without spamming on every poll.

### Decoder exit guard and prebuffer timeout

`DecoderExitGuard` is held for the whole life of every decoder thread and sets `eof` on any exit — a normal return, an `Err`, or an unwinding panic — so `wait_until_prebuffered` and the drain path can never hang on a decoder that stopped without reaching its usual return path; a panic that is not a deliberate cancel also marks the track failed with an internal-error message. Before a stream is built, the controller waits up to `PREBUFFER_TIMEOUT` (30 s; `wait_until_prebuffered_within`) for the ring buffer to fill enough to start playback; a NAS spin-up slower than that refuses the start with an error instead of blocking indefinitely, and the user can retry.

### Device volume

`AudioPlayer::set_volume` sets the *output device's own* CoreAudio volume (`coreaudio::set_device_volume`), never an internal software gain — there is no per-track or master software volume anywhere in the pipeline. The target device is the active output when a track is playing, falling back to the currently selected-but-not-yet-playing device (`volume_target_uid`); a device with no settable volume control disables the slider with an explanation instead of silently doing nothing. On a device with independent left/right elements, `scale_channel_volumes` scales both channels by the same ratio so the slider preserves the device's existing balance rather than forcing it to equal channels — except when both channels already read zero, where there is nothing to scale a ratio from and the new level is applied to both channels equally (see README "Known limits").

### Sample-rate repair

A FLAC at a non-standard sample rate (`audio::rate_repair::STANDARD_SAMPLE_RATES`: 8000, 11025, 12000, 16000, 22050, 24000, 32000, 44100, 48000, 88200, 96000, 176400, 192000, 352800, 384000) can never play: the strict route requests the file's exact rate and `exact_output_config` refuses when the device does not offer it (verified with cpal on this machine — FiiO K11, MacBook and Studio Display speakers all list only 44.1/48/88.2/96 kHz and up, so a 37 800 Hz PS1/XA rip fails with "The selected output does not support stereo at exactly 37800 Hz."). The playback path deliberately stays strict ("no hidden sample-rate fallback"), so the fix is a one-time on-disk conversion at scan time instead.

- **Detection** is in the scanner's phase 1 (`probe_phase`): `needs_rate_repair(&AudioInfo)` (FLAC, non-whitelisted rate) hands the path to `library::repair::RepairWorker` (thread `lime-rate-repair`, one file at a time, `catch_unwind`-guarded) and holds that one track out of the batch's `Probed`. Other files of the batch are unaffected. When the worker reports (`RepairDone`), `resume_after_repair` sends `RateRepaired`/`RateRepairFailed`, **re-probes the file**, and sends it through the ordinary `Probed` → phase 2 path, so a track only ever enters the library/queue with the `AudioInfo` of the file actually on disk (no stale-rate `TrackKey`/queue entries). A held track counts toward its batch's `remaining`, so `BatchDone` waits for it; phase-2 items are therefore tagged with their batch id (`(u64, Phase2Item)`, `finish_item`) instead of assuming the front batch, and a batch waiting on a repair can finish after a later batch. CUE-claimed files (`expand_cue_sheets_for_paths`) are never repaired.
- **Engine** (`src/audio/rate_repair.rs`, `repair_flac_sample_rate`): target rate is the nearest of 44.1/48/88.2/96/176.4/192/352.8/384 kHz in ratio terms (`repair_target_rate`; 37 800 → 44 100). Streams symphonia decode → `rubato::Fft` (f64) → quantize to the source bit depth → `flacenc` (`ResamplingSource` implements `flacenc::source::Source`, so memory is bounded by the chunk size). Tags/cover are preserved by copying the original's `VORBIS_COMMENT`/`PICTURE`/`APPLICATION` blocks verbatim into the new file (STREAMINFO regenerated; PADDING/SEEKTABLE dropped); an embedded `CUESHEET` (sample offsets at the old rate) or a leading ID3v2 makes it refuse instead. Order of effects: temp file beside the original (hidden `.lime-rate-repair-<name>`; fails fast on a read-only volume) → encode → `flush_durably` (`F_FULLFSYNC`, falling back to `fsync`; a volume with neither refuses the repair, see the SMB gotcha below) → `verify_repaired` (decode end to end; rate, channels, bit depth ≤ original, frame count within max(2 frames, 1 ms), source decoded to its declared duration, kept blocks byte-identical) → back up the original (`<stem>.original-<rate>-<pathhash>.flac`, identical existing backup reused; the backup file and its directory are flushed with `flush_durably` before this step returns, so the rename never runs ahead of a durable backup) → set permissions → atomic `rename`. Symlinks are resolved first. Anything failing before the rename leaves the original untouched and removes the temp file.
- **Gotcha:** `flacenc` writes the shorter final block as STREAMINFO's *minimum* block size, and symphonia only accepts fixed-size frames when min == max, so it refused to open the encoder's output. `split_encoded_stream` sets min = max (the FLAC spec defines min as excluding the last block).
- **Gotcha:** on macOS Rust's `File::sync_all` is `fcntl(F_FULLFSYNC)`, which smbfs (a NAS share) does not implement: it fails with ENOTSUP (errno 45), so every repair on an SMB volume aborted at the flush and left the original unchanged. `flush_durably` (`flush_with_fallback`) retries with plain `fsync(2)` (`libc`, unix-only direct dependency) on ENOTSUP/EOPNOTSUPP only. Every other flush error (EIO, ENOSPC, EDQUOT, ...) fails the repair, and so does a volume where `fsync` is unsupported too (`flush_error` → `RepairError::Unsupported`): the flush is the only point where a deferred write error can still surface (`File`'s drop swallows `close` errors), and `verify_repaired` re-reads the file through this client's own cache, not from what the server stored, so it cannot stand in for the flush. The local backup gets the same flush (file and directory entry: `flush_path_durably`, `flush_directory`) before the rename over the original, which a network server commits at once. Verified end to end on a copy on a real SMB share with `repair_real_file` (37 800 → 44 100 Hz, tags and cover byte-identical, backup byte-identical, no temp file left): only the flush needed the fallback; the verify, the backup into the local directory, `set_permissions` and the `rename` over the existing file all work there.
- **Reporting** follows "Diagnostic vs Status events": every outcome is a `DIAG` line on stderr (`write_diagnostic` in `main.rs`), and `RepairNotes` (per batch, `library/repair.rs`) becomes one status line at `BatchDone` (a status set when the repair finishes would be overwritten by the batch's route-status restore); repair failures are left out of the status line for `BatchKind::StartupRestore`. A failed path is remembered by the worker for the session (no retry loop).
- **Setting**: `Preferences::repair_nonstandard_sample_rates` (default `true`, `settings.json` only — the UI has no library-settings surface, the Hog mode toggle being an output setting). `LibraryScanner::new()` never repairs; `main.rs` builds `LibraryScanner::with_rate_repair(RateRepairConfig { backup_dir })` (`settings::rate_repair_backup_dir`, `<data_dir>/rate-repair-backups`) when the setting is on. Cargo `[profile.dev.package.*]` optimizes flacenc/rubato/rustfft so a debug build does not take about a minute per track.
- Known gaps: FLAC only (WAV/MP3/WavPack untouched); CUE-claimed files; tracks removed via "Remove from Library" are still repaired if their folder is rescanned (the scanner does not know the exclusion set); a repaired file has no seek table and gets no dither.

### Settings

`src/settings.rs` persists `Preferences { output_device_id, hog_mode_enabled, repair_nonstandard_sample_rates }` as JSON at `ProjectDirs::from("com", "Lime Player", "Lime Player")` config dir `/settings.json`. Load/save errors are reported, not fatal.

### Persistent library

`src/library/store.rs` persists `LibrarySources { files, folders, cue_files }` as JSON at the same `ProjectDirs` config dir, `/library.json`, written atomically (temp file + rename). It records only *which paths* to re-scan — individually opened files, added folders, and directly opened `.cue` sheets (`add_cue_file`, deduped by exact path like `files`) — never decoded tags, durations or artwork; the `Library`/`TrackRecord` values built from them (cue-derived tracks included) stay session-only and are rebuilt every startup by re-running those paths through `LibraryScanner`, tagged `BatchKind::StartupRestore` (`main.rs`) so the restore only fills the library and never enqueues or plays anything. A path that fails to probe (e.g. an unmounted NAS share) is kept in `library.json` regardless — nothing ever prunes an entry — and is surfaced as one aggregate status line ("N saved tracks are unavailable…") instead of a per-file one. A `library.json` load failure is reported the same way and never triggers an overwrite of the file. "Open Folder…" (top bar, next to Open Files) recursively walks a chosen directory off the UI thread (`src/library/walker.rs`, via `LibraryScanner::scan_folder` on its own thread so it never blocks other in-flight scans), skipping hidden/`._` files, directories named `*.wv`, and symlink loops, and accepting the same extensions as Open Files; found tracks are added to the library only, never enqueued, and the folder is persisted for re-walking at the next startup.

### Library exclusions ("Remove from Library")

Every album card (`AlbumTile`, `ui/widgets.slint`) carries a three-dot menu with one item, "Remove from Library" (`Theme.danger`, `Icons.more-vertical`/`Icons.trash`). It is non-destructive — it never touches a file on disk — and library-only: `AppState::remove_album` (`Library::remove_album` plus forgetting the album's cached pictures) drops the album's tracks from the in-memory session `Library` and returns their `TrackKey`s, which `main.rs`'s `on_remove_album_requested` persists into `LibrarySources.excluded_tracks` (a `HashSet<TrackKey>` field of `library.json`, `#[serde(default)]` so an older `library.json` still loads). Exclusion is keyed on the exact `TrackKey` (path + CUE sample-frame sub-range), not a bare path, so removing one CUE sub-range track never excludes its siblings carved from the same physical file. `LibraryEvent::Probed`/`Scanned` are filtered against this set (`exclude_removed_tracks`, `LibrarySources::is_excluded`) before they can reach the library, so a later rescan of an already-persisted `files`/`folders`/`cue_files` entry — chiefly the startup restore — never brings an excluded track back. Explicitly re-opening the same file(s) or folder via "Open Files…"/"Open Folder…" lifts the exclusion for those paths first (`LibrarySources::include_path`/`include_folder`, called before `scan()`/`scan_folder()` is even dispatched): an explicit user action always overrides a past removal. Every `scan()`/`scan_folder()` call also receives a snapshot of the exclusion set (taken after that lift) so the scanner never spends an album's picture on a record `main.rs` is about to drop — see "Album grouping" -> "Artwork"; the events themselves are still filtered on the UI thread, not in the scanner. Removal never touches `AudioPlayer`'s queue or active stream — the library and playback are separate, session-only state (see "Session library and view layer" above) — so a track from the removed album that is currently playing or queued keeps playing/queued untouched; if the album's own detail page is open, `Navigation::remove_album` navigates back automatically, and the status line reports `Removed "<album>" from the library.`.

### Unified title bar (macOS)

`slint`'s `unstable-winit-030` feature (`Cargo.toml`) is enabled unconditionally, but only used under `cfg(target_os = "macos")` in `main.rs`. Before `MainWindow::new()`, `slint::BackendSelector::new().with_winit_window_attributes_hook(...)` hides the native title bar (`WindowAttributesExtMacOS::with_titlebar_transparent`/`with_title_hidden`/`with_fullsize_content_view`) so the content view extends to the top of the window; `MainWindow.title` stays `"Lime Player"` (macOS still uses it for Mission Control and the Window menu). `window.set_unified_title_bar(true)` then drives `ui/app.slint`'s `MainWindow.unified-title-bar` property, which only exists on macOS — every other platform leaves it `false` and keeps Slint's normal decorated window, reserving no traffic-light space. When `true`, `Sidebar` reserves its top 52 px for the traffic lights and `TopBar` shows the window title on that same row; both carry their own drag `TouchArea` over that empty space (`window-drag-requested`, handled in `main.rs` via `slint::winit_030::WinitWindowAccessor::with_winit_window` and winit's `Window::drag_window()`), and `TopBar`'s doubles as a double-click zoom (`window-zoom-requested`, `Window::set_maximized`), matching a native title bar. All real buttons and the search field sit in the same tree after these `TouchArea`s, so they still receive clicks. The offscreen snapshot harness (`src/ui_snapshot.rs`) renders one Home scenario with `unified-title-bar: true` for visual review; the software renderer never draws native traffic lights, so only the reserved space and alignment can be checked that way.

## Invariants

- Never change the macOS system-wide default output device; always target the selected CPAL device.
- Prefer refusing playback with an error over silently degrading: no hidden sample-rate fallback, no format conversion in the strict route, no playing WavPack hybrid (`.wvc`) streams, no acquiring Hog mode from another owner.
- The 90 ms guard is software-side only. Do not claim verified hardware drain, bit-perfect USB output, or a <200 ms rate transition — those are unverified on device (see README "Known limits").
- The library's *decoded* contents (tags, durations, artwork, and cue-derived tracks) are session-only and rebuilt by re-scanning at each startup; only the set of source paths (`library.json`, individually opened files, added folders, and directly opened `.cue` sheets) is persisted across restarts.
- The OS media session is created only in `main()`; no test or the snapshot harness constructs one, and its handlers only `send` into the channel (no UI or player state is touched off the UI thread). Do not claim media-key or Now Playing behavior as verified on a real keyboard/Control Center session — see "Media controls".
